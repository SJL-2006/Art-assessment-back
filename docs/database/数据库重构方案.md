## 项 1：清理未用的 Django group/permission 表

**现状**：`auth_group` / `auth_group_permissions` / `users_user_groups` / `users_user_user_permissions` 共 4 张表，全部 0 行。项目用 JWT + 自定义 `RolePermission`（`apps/common/permissions.py`），从不使用 Django 的 Group/Permission/`has_perm`。

**根因**：`User` 继承 `AbstractUser`，默认带上 `groups` / `user_permissions` 两个多对多（见 `apps/users/migrations/0001_initial.py:40-43`）。

**变更方案（二选一）**：

- **方案 A（推荐）**：**保留不动**。4 张表 0 行、无害、Django 内部会用到 `auth` 框架；删它要把 `User` 从 `AbstractUser` 换成 `AbstractBaseUser`（重写密码哈希/认证/Manager），收益仅为「少 4 张空表」，风险收益不成比例。
- **方案 B（要极致干净才选）**：自定义 User（`AbstractBaseUser` 不带 `PermissionsMixin`），手动补 `is_staff`/`is_superuser`，删除 4 表。需重写 `LoginView`/注册/权限里所有依赖 `User` 的逻辑。

**影响范围**（方案 B）：`apps/users/models.py`、`serializers.py`、`views.py`、`views_accounts.py`、全站 `request.user` 相关。
**回滚**：恢复 `AbstractUser` 继承 + `makemigrations` 重建 4 表。

**结论**：除非你要一个「零死表」的洁癖 schema，否则跳过。

## 项 3：证书两表 —— 建议「改名」而非「合并」

**现状**：两张表字段确实有重叠，但**工作流本质不同**：

| | `exam_certificate`（4 行） | `exam_uploaded_certificate`（1 行） |
|---|---|---|
| 来源 | 系统测评后自动生成 | 学生手动上传图片 |
| 关键字段 | `file`、`sheet_id`(关联答卷) | `cert_type/issuer/obtained_at/image/note/status/review_comment/reviewed_at/reviewer_id` |
| 流程 | 无审核，直接生成 | 有审核（pending→approved/rejected） |
| 路由 | `/exam/certificates/` | `/exam/cert-uploads/` |

**结论**：二者是「系统证书」和「学生上传证书」两个独立实体，**不建议合并**（合并会引入大量可空字段 + 审核流程与生成流程耦合）。

**变更方案（推荐）**：仅**改名**消除歧义 —— `exam_uploaded_certificate` → `exam_student_certificate`（模型 `UploadedCertificate` → `StudentCertificate`），路由 `/exam/cert-uploads/` 可保持（避免动前端）或改为 `/exam/student-certificates/`。

**影响范围**：`apps/exam/models.py`、`serializers.py`、`student_views.py`、`urls.py`、`migrations`；前端 `api.js` 若路由改名需同步。
**数据迁移**：`RENAME TABLE` 或迁移改名，1 行数据自动跟随。
**回滚**：反向 rename。

**结论**：低风险，改命名即可。

## 项 4：引入「学科」维度（核心重构）

**现状（问题根源）**：`qb_course.code` 用 varchar 存学科代码，且**多门课程共用同一 code**（音乐鉴赏/初中音乐/高中音乐/小学音乐 的 code 都是 `music`），`Paper.subject` 也是 varchar（music/art）。导致代码里一堆「按 code 聚合 / 中文名映射」的补丁：

- `apps/exam/views.py`：`SUBJECT_TO_COURSE_NAME`、`SUBJECT_ALIASES`、`normalize_subject`、`_resolve_course`（取题量最多的一条课程）
- `apps/exam/practice_views.py`：`_subject_questions`（按 course__code 聚合）
- `apps/questionbank/views.py:108-112`：按 `course__code` 聚合过滤
- `apps/exam/student_views.py:40`、`search_views.py:69`、`users/views.py:84`：读 `course.code`

**变更方案**：新增学科维度，把「学科」从「课程」中解耦。

1. **新增表 `qb_subject`（学科）**：`id`、`code`(uniq，如 music/art)、`name`(音乐/美术)、审计字段。
2. **`qb_course` 增加 `subject_id` FK → qb_subject**（替代/兼容现有 `code`）。`code` 字段保留过渡期，后续删除。
3. **`qb_question` 增加 `subject_id` FK → qb_subject**（可冗余，避免每次 join 课程取学科；或通过 course 间接取）。
4. **`exam_paper` 的 `subject` 字段改为 FK → qb_subject**（或保留 varchar + 代码统一从 subject 表取）。
5. 所有 `course__code` / `SUBJECT_TO_COURSE_NAME` / `SUBJECT_ALIASES` 逻辑改写为基于 `subject`。

**数据迁移**：
```sql
-- 建学科表 + 灌数据
INSERT INTO qb_subject(code, name) VALUES ('music','音乐'), ('art','美术');
-- 回填课程
UPDATE qb_course c JOIN qb_subject s ON c.code = s.code SET c.subject_id = s.id;
-- 回填试题（经由课程）
UPDATE qb_question q JOIN qb_course c ON q.course_id = c.id
  JOIN qb_subject s ON c.subject_id = s.id SET q.subject_id = s.id;
```

**影响范围（大）**：`questionbank`（Course/Question 模型 + views）、`exam`（Paper 模型 + views/practice_views/student_views/search_views/serializers）、`users/views.py`；前端组卷/试卷/练习相关字段若依赖 `subject` 字符串，需同步。
**回滚**：保留旧 `code` 字段到确认稳定后，再删。

**风险**：高。涉及组卷核心逻辑，需回归验证（practice/random、auto-generate、题库筛选、成绩曲线）。

**建议**：分两步 —— 先「加 subject 表 + 回填 + 双轨并存」，稳定后再「删 code 旧逻辑」。**这是本次重构唯一真正值得动的高价值项**。

## 项 5：重构试卷发布范围 scope

**现状**：`exam_paper_publish` 用 `scope_type`(class/school/grade/region) + 3 个可空 FK（`target_school`/`target_class`/`target_region`）+ `grade` 表达「发布给谁」，serializer 里做了交叉校验（`serializers.py:186-198`）。

**评估**：这是 Django 里常见且**可接受**的建模方式（有 serializer 校验兜底，能表达「班级/学校/年级/区域」四种范围）。重构收益低。

**变更方案（可选，二选一）**：
- **方案 A（推荐）**：**保持现状**，仅补齐文档 + 必要时的校验完善。低风险。

**影响范围**：`apps/exam/models.py`、`serializers.py`、`answer_views.py`、`admin.py`、`seed_demo.py`。
**数据迁移**（方案 B）：把 29 行 scope 拆到新表。
**回滚**：还原 3-FK 结构。

**结论**：**建议暂缓**，除非有「多范围发布」的新需求。
